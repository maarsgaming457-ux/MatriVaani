# MatriVaani NMT Memory Analysis

## 1. Context
The overarching MatriVaani Android application has a strict global memory ceiling of `< 2.0 GB`, with a preferred operating range of `1.0–1.5 GB`. The application must run three heavy ML components: ASR, NMT, and TTS.

## 2. NMT Foundation Model Footprint
The chosen foundation model, **AI4Bharat/IndicTrans2**, is exceptionally capable at Hindi-Santhali translation but possesses **~1.1 Billion parameters**.

### FP32 (Full Precision)
- **Model Size on Disk**: ~4.4 GB
- **Inference RAM**: ~4.5 GB - 5.0 GB
- **Training (LoRA) VRAM**: > 16 GB
- **Android Feasibility**: IMPOSSIBLE

### INT8 (8-bit Quantization)
- **Model Size on Disk**: ~1.1 GB
- **Inference RAM**: ~1.4 GB - 1.8 GB
- **Android Feasibility**: BORDERLINE

## 3. Simultaneous Execution Constraints
If NMT (INT8) requires ~1.5 GB, and ASR (Phase 3 wav2vec2-base) requires ~850 MB, they cannot coexist in memory (2.35 GB total) without breaching the 2.0 GB ceiling, even before accounting for TTS and OS overhead.

## 4. Required Optimizations
To meet the MatriVaani deployment constraints, we must employ the following strategies (detailed further in `NMT_DEPLOYMENT_PLAN.md`):

1. **Sequential Lifecycle Management**: Models must be aggressively unloaded from RAM immediately after their portion of the pipeline executes.
2. **ONNX Runtime (ORT)**: Exporting to ONNX format with graph optimizations specifically tailored for ARM CPUs to lower peak activation memory.
3. **Knowledge Distillation**: The optimal long-term solution. We must train a smaller student model (e.g., ~200M-300M parameters) specifically on the Hindi-Santhali educational pairs generated by the 1.1B IndicTrans2 teacher.
